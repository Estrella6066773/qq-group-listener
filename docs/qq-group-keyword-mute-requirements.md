## 1. 需求

### R1 关键词触发（替代 always-on）
不采用「群消息全量唤醒模型」的方式。改为**关键词硬触发**：仅当群消息命中指定关键词时，才唤醒机器人。

- 关键词集：一切成瘾品（**酒除外**）。词表见 `qq-group-trigger-keywords.md`。
- 被 @ 时仍应正常唤醒（保留原行为）。
- 未命中关键词的普通消息：**不唤醒模型、不回复**；但建议仍**静默入缓冲区**（供后续判断，见关联项目）。

### R2 自动禁言
在机器人具备**群管理员**身份后，按关键词命中频次自动禁言：

| 条件 | 动作 |
|---|---|
| 同一人在 **30 分钟**内命中关键词 **> 3 次** | 禁言该成员 **1 分钟** |
| 同一人 **当天**已被禁言 **> 3 次** | 当天**余下每次**禁言时长延长为 **10 分钟** |

- 计数窗口：30 分钟为**滑动窗口**；「当天」按 `Asia/Shanghai` 自然日。
- 计数主体：**按成员**（`member_openid`）分别计数。
- 触发时的禁言时长取决于「当天已禁言次数」：≤3 次 → 1 分钟；>3 次 → 10 分钟。
- 需持久化状态（30 分钟窗口计数、当日禁言次数），跨重启不丢。

## 2. 必须先纠正的误解（重要）

> ❌ 「安装 `tencent-channel-community`（腾讯频道）skill 就能获得本群管理员权限」——**不成立**。

- `tencent-channel-community` 管理的是 **腾讯频道（QQ 频道 / guild）**，命令域只有 `feed` 与 `manage`，操作对象是**频道、版块、频道帖子、频道成员**。
- 本会话所在的是 **QQ 群**（群聊，`group_openid`），与「QQ 频道」是**两个不同产品**，接口不通用。
- 因此：该 skill **无法**管理本群，也**不会**赋予本群管理员权限。

**真正的管理员来源**：由**群主**把机器人**设为群管理员**（QQ 群设置 → 群机器人 → 该机器人 → 设为管理员）。这与任何 skill 无关，是平台侧角色授予。

## 3. 已验证的事实（含证据）

### 3.1 QQ 群禁言 API 真实存在
官方文档（`bot.q.qq.com/wiki`，更新时间 2026-09-03）明确：

- **查询群禁言状态**：`GET /v2/groups/{group_openid}/restrict_chat_setting`
- **设置群成员禁言**：`POST /v2/groups/{group_openid}/restrict_chat_setting`
  - 频率限制 **60 QPM**
  - 前置条件：**机器人需拥有群管理员身份**；最大禁言时长 **30 天**
  - 请求体：
    ```json
    {
      "members": [
        { "op": "add", "member_openid": "EC58...", "mute_expire_at": "2026-08-05T11:23:05+08:00" }
      ]
    }
    ```
  - `members` 单次**不超过 20 个**；`op` 取值 `add`（增加）/`update`（更新到期时间）/`del`（解除）
  - `mute_expire_at`：**RFC3339 绝对时间**（非时长）；`op=del` 时可传空串立即解禁
  - 限制：**只能操作普通成员**，不能操作群主、管理员、机器人
- 错误码提示：`850018` 群被禁言或机器人被禁言；`40054003` 机器人不是群成员。

### 3.2 调用通道已就绪
QQ 插件 `@tencent-connect/openclaw-qqbot` 注册了通用平台 API 工具 **`qqbot_platform_api`**（自动带鉴权 Token，支持 GET/POST/PUT/PATCH/DELETE）。可在群消息会话中直接调用上述禁言接口，**无需额外 skill**。

### 3.3 关键词触发存在限制（关键）
在本机插件源码中核实：

- 插件的群唤醒中间件为 `bot.use(mentionGate())`，其判定为：
  `wasMentioned = 收到 GROUP_AT_MESSAGE_CREATE 事件 || mentions 中含 is_you || 内容含 <@appId>`
- **`mentionPatterns` 未被该中间件消费**；它只出现在 `resolveMentionPatterns → buildClawCfg → mention_patterns`，用于**回传给 QQ 平台的互动配置**。
- 结论：在 QQ 群，**配置 `mentionPatterns` 无法实现「关键词唤醒」**。
- 且 `requireMention: true` 时，非 @ 消息会被中间件 `ctx.stop()` 丢弃（仅按 `historyLimit` 留存为上下文），**永远到不了模型**。

**因此 R1 需要两选一：**
1. **插件/钩子方案**（推荐，即关联文档中的「补丁插件」）：以 `before_dispatch` 等 seam 在入站层做关键词判定——命中放行，未命中静默入缓冲区（零模型调用）。
2. 妥协方案：保留 always-on（`requireMention: false`），由模型自行判断——**代价是每条消息都产生一次模型调用**（已确认不受欢迎）。

> R2 依赖 R1：机器人必须先「看到」消息（无论哪种方案），才可能计数与禁言。

## 4. 状态设计（建议）

- 存储：本地 JSON 文件（工作区 `state/`），原子写入。
- 结构（示意）：
  ```json
  {
    "keywords": { "version": "v1.0" },
    "hitWindow": { "<member_openid>": [ 1758500000000, 1758500120000 ] },
    "muteCountToday": { "date": "2026-09-22", "byMember": { "<member_openid>": 2 } }
  }
  ```
- 30 分钟滑动窗口：只保留最近 30 分钟内的命中时间戳。
- 跨日：`date` 变更时重置 `byMember`。
- 幂等：同一 `message_id` 不重复计数。

## 5. 验收标准

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| B1 | 关键词唤醒 | 群消息命中关键词 → 机器人被唤醒并回应；未命中 → 无模型调用 |
| B2 | @ 仍有效 | 被 @ 时正常唤醒 |
| B3 | 计数正确 | 同一人 30 分钟内第 4 次命中触发禁言；同条消息多词只计 1 次 |
| B4 | 禁言时长 | 当日禁言 ≤3 次 → 1 分钟；第 4 次起 → 10 分钟 |
| B5 | 权限容错 | 机器人非管理员时，禁言失败应有明确日志，不静默、不误判 |
| B6 | 状态持久 | 重启后窗口计数与当日次数不丢 |
| B7 | 不误伤 | 未命中关键词的日常闲聊不触发任何回复/禁言 |
